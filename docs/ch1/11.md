# 11. 3D 로 먼저 짓다

> **지난 장면** 10강에서 공정표에 사람과 돈을 싣고 기준선 BL0을 저장했다. 같은 주에 원자로건물 기초 통합 모델이 올라왔고, BIM 회의 안건 첫 줄에 "간섭 23건"이 적혀 있다.

## 회의실 화면의 모델

목요일 오후 주간 BIM 회의. 회의실 대형 화면에 원자로건물 기초 매트가 3D로 떠 있다. 철근 한 가닥, 매입판 한 장, 바닥을 지나는 슬리브 하나까지 따로 선택된다. 참석자는 공사 담당, 공정 담당, 설계사 현장 주재원, 철근·매입물 협력사 반장이다.

모델은 한 회사가 한 프로그램으로 만든 것이 아니다. 여러 파일이 겹쳐 있다.

| 모델 파일 | 작성 | 도구 | 담긴 것 |
|---|---|---|---|
| GR1-RB-C-MDL-0101 | 설계사 | Revit | 콘크리트 형상, 매입판, 앵커볼트 |
| GR1-RB-C-MDL-0102 | 철근 상세 협력사 | Tekla Structures | 기초 상·하부 철근, 커플러 |
| GR1-RB-M-MDL-0201 | 설계사 | Revit | 바닥 관통 슬리브, 배관 지지대 기초 |
| GR1-RB-FED-0001 | 당사 BIM 담당 | Navisworks | 위 세 파일을 겹친 검토용 파일 |

Revit은 건물 형상과 설비를 설계하는 모델링 도구, Tekla는 철근·철골을 실제 가공·설치 수준까지 상세화하는 도구다. Navisworks는 모델을 직접 그리기보다 여러 모델을 불러와 겹치고, 부딪히는 곳을 찾고, 공정과 연결해 보는 검토 도구다.

::: term 건설정보모델링 | Building Information Modeling | BIM | 빔
건물을 3D 형상과 함께 각 객체의 속성(재료, 규격, 위치, 설치 시점 등)을 담은 모델로 만들고, 설계·시공·운영에서 그 정보를 함께 쓰는 방식. 도면은 이 모델에서 뽑아내는 결과물 중 하나가 된다.
EN: "All embedments shall be modeled in BIM before shop drawing submittal."
:::

::: term 통합 모델 | Federated Model | - | 통합본, 페더레이티드
분야·회사별로 따로 만든 모델 파일을 원본은 그대로 두고 한 좌표계에 겹쳐 놓은 검토용 모델. 각 원본의 책임은 작성자에게 남는다. 간섭검토와 4D는 이 통합 모델에서 한다.
EN: "The federated model is refreshed every Wednesday for the BIM coordination meeting."
:::

서로 다른 프로그램의 모델을 겹칠 수 있는 이유는 공통 형식이 있기 때문이다. 철근 협력사는 Tekla 모델을 IFC로 내보내 올렸다. 05강의 시공용 발행(IFC)과 약어만 같다.

::: term IFC 파일 | Industry Foundation Classes | IFC | 아이에프씨
BIM 모델을 특정 회사 프로그램에 묶이지 않고 주고받기 위한 공개 데이터 형식. buildingSMART가 관리하고 ISO 16739로 국제표준이 됐다. 형상뿐 아니라 "이 객체는 벽이다, 철근이다" 같은 분류와 속성도 함께 담는다.
EN: "Rebar models shall be delivered in IFC format for federation."
:::

모델이 얼마나 자세한지도 파일마다 다르다. 설계사 Revit 모델의 매입판은 위치와 크기가 정확하지만 스터드 볼트는 없다. Tekla 철근 모델은 가닥 하나, 커플러 하나까지 있다. 회의 자료의 모델 상세수준 표에는 "매입판 LOD 350, 철근 LOD 400"이라고 적혀 있다.

::: term 모델 상세수준 | Level of Development | LOD | 엘오디
모델 객체의 형상과 정보를 얼마나 믿고 쓸 수 있는지 단계로 나타낸 것. 흔히 BIMForum의 LOD Specification에 따라 100(개략)부터 400(제작·설치 수준)까지 나눈다. 350은 다른 분야와 만나는 접합부까지 모델링한 단계다. 그림이 얼마나 자세한가(Level of Detail)와는 다른 개념이다.
EN: "Embedded plates are modeled to LOD 350 including interfaces with rebar."
:::

## 23건을 하나씩

BIM 담당이 Navisworks의 Clash Detective 결과를 띄운다.

```text
Clash Detective — GR1-RB-FED-0001          Run: 2주차 목요일
Test                               Type        Tolerance  Clashes
T1 철근(Tekla) vs 매입판(Revit)      Hard        0 mm         9
T2 철근(Tekla) vs 관통 슬리브        Hard        0 mm         6
T3 매입판 vs 배관 지지대 기초          Clearance   50 mm        5
T4 앵커볼트 vs 철근(Tekla)          Hard        0 mm         3
                                                   Total     23
Status: New 23 / Active 0 / Reviewed 0 / Approved 0 / Resolved 0
```

Hard는 두 객체가 실제로 겹친 경우다. Clearance는 겹치지 않았어도 정한 거리보다 가까운 경우다. T3의 50mm는 이 현장 BIM 수행계획서에 정한 검토 조건이다. 허용오차가 아니라 "이보다 가까우면 사람이 보고 판단한다"는 기준이다.

::: term 간섭검토 | Clash Detection | - | 간섭 체크, 클래시
통합 모델에서 서로 다른 객체가 겹치거나(Hard) 정한 이격 거리보다 가까운(Clearance) 곳을 자동으로 찾고, 회의에서 하나씩 원인과 조치를 정하는 일. 자동으로 찾은 건수 자체보다 각 건을 누가 언제 어떻게 처리할지 정하는 것이 핵심이다.
EN: "Clash T1-007 was reviewed and assigned to the rebar detailer for resolution."
:::

회의는 23건을 한 건씩 화면에 띄워 확인한다. 끝났을 때 결과는 이렇다.

| 처리 | 건수 | 내용 |
|---|---|---|
| 실제 간섭 아님 (Approved) | 4 | 모델 작성 오류 — 슬리브가 두 번 그려짐 등 |
| 철근 상세 수정 (Active) | 11 | 철근 간격 안에서 위치를 옮겨 피함 — 철근 협력사 수정 |
| 설계 확인 필요 (Active) | 5 | 매입판과 지지대 기초 간격 — RFI로 설계사 확인 |
| 시공 순서로 해결 (Reviewed) | 3 | 앵커볼트 템플릿 설치 후 철근 배근 — 작업 순서 표기 |
| 합계 | 23 | |

<details><summary>❓ 먼저 생각해 보기 — 간섭검토를 실제 타설 두 달 전에 하는 이유는 무엇일까?</summary>

간섭을 현장에서 발견하면 이미 가공된 철근을 다시 자르거나, 묻힌 매입물을 옮겨야 한다. 철근은 가공표대로 공장에서 잘려 오고, 매입판은 제작에 시간이 걸린다. 그래서 가공·제작 발주 전에 모델에서 부딪혀 보고, 설계 확인이 필요한 건은 RFI 답변을 받을 시간까지 남겨 둬야 한다. 기초 매트처럼 한번 부으면 되돌릴 수 없는 곳일수록 이 순서가 중요하다.
</details>

## 시간을 붙인 모델

회의 마지막 안건은 공정 담당이 띄운다. Navisworks의 TimeLiner에서 P6 Activity를 모델 객체에 연결한 결과다. `U1-RB-FDN-1030`(상부 철근)에는 Tekla 상부 철근 객체가, `U1-RB-FDN-1040`(매입물)에는 Revit 매입판이 연결돼 있다. 재생 버튼을 누르면 날짜가 흐르면서 객체가 공정 순서대로 나타난다. 상부 철근이 깔리는 중간에 매입판이 들어오는 장면에서 반장이 손을 든다. 그 위치는 철근이 촘촘해 매입판을 들고 들어갈 길이 없다는 지적이다. 공정 담당은 그 구역의 매입물을 먼저 넣는 순서로 관계를 다시 검토하기로 메모한다.

::: term 4D 시뮬레이션 | 4D Simulation (TimeLiner) | 4D | 포디
3D 모델 객체에 공정표의 Activity 날짜를 연결해 시간 순서대로 지어지는 모습을 재생하는 것. Navisworks에서는 TimeLiner 기능으로 한다. 공정표의 논리가 현장에서 실제로 가능한 순서인지, 장비·작업 공간이 겹치지 않는지를 눈으로 확인한다.
EN: "The 4D simulation revealed an access conflict between embedments and top rebar."
:::

## 실제로는

Autodesk가 공개한 고객 사례에 따르면 현대건설은 Revit과 Navisworks를 BIM 기반 보고, 이슈 검토, 시공상세도 검증에 활용했다. 또 현대건설은 2024년 Trimble과 함께 철골·PC 공사를 위한 BIM 기반 공정관리 프로그램을 공동 개발했다고 밝혔다. Tekla가 바로 Trimble의 제품이다. 이야기 속 회의 장면은 가상이지만, 쓰는 도구와 일의 흐름은 이런 실제 사례에 가깝게 그렸다.

## 실습

P4 — Navisworks는 Windows 전용 유료 프로그램이다. 실습은 Blender의 무료 BIM 추가 기능인 Bonsai로 한다. Bonsai는 IfcOpenShell 기반이라 IFC 파일을 바로 열고 간섭검토(IfcClash)를 돌릴 수 있다. 예제 IFC 두 개를 불러와 Hard 간섭 건수를 확인하고, 한 건을 골라 원인과 조치를 한 줄로 적는다. (practice/README.md)

## 다음 장면

간섭 5건은 RFI로 설계사에 넘어갔고, 나머지는 철근 협력사가 모델을 고친다. 모델이 정리되면 다음은 실제로 지을 때 누가 어느 단계에서 무엇을 검사할지 약속하는 문서다. 품질 담당이 기초 매트 검사·시험계획서 초안을 돌린다.

## 확인 문제

<details><summary>1. Hard 간섭과 Clearance 간섭은 어떻게 다른가? T3의 50mm는 허용오차인가?</summary>

Hard는 두 객체가 실제로 겹친 경우, Clearance는 겹치지 않았어도 정한 이격 거리보다 가까운 경우다. 50mm는 허용오차가 아니라 "이보다 가까우면 사람이 검토한다"는 검토 조건이며, 이 현장 BIM 수행계획서에서 정한 값이다.
</details>

<details><summary>2. 통합 모델에서 철근 간섭을 발견했다. 통합 모델 파일을 직접 고치면 안 되는 이유는?</summary>

통합 모델은 원본 모델들을 겹쳐 놓은 검토용 파일이다. 원본의 책임은 작성자(철근 상세 협력사)에게 있으므로, 원본 Tekla 모델을 고쳐 다시 IFC로 올려야 다음 통합 때 수정이 남는다. 통합본만 고치면 다음 주에 같은 간섭이 다시 나온다.
</details>

<details><summary>3. 4D 시뮬레이션이 간섭검토로는 찾을 수 없는 문제를 찾은 예를 이번 강에서 들어라.</summary>

상부 철근이 깔린 뒤 매입판을 넣는 순서에서 작업자가 매입판을 들고 들어갈 공간이 없다는 문제다. 객체끼리 겹치지는 않으므로 간섭검토에서는 나오지 않는다. 시간 순서를 붙여 봐야 드러난다.
</details>

<details><summary>4. 공정표의 Activity를 나눌 때 기간을 정하는 Original Duration과 Calendar의 관계를 설명하라. (07강)</summary>

Original Duration은 작업일 수로 정한 기간이고, Calendar는 어느 날이 작업일인지(주 5일·6일, 휴일 등)를 정한다. 같은 10d라도 어느 달력을 쓰느냐에 따라 실제 종료 날짜가 달라진다.
</details>

<details><summary>5. 문서 송부(Transmittal)는 왜 따로 기록으로 남기는가? (05강)</summary>

어떤 문서의 어떤 Rev를 언제 누구에게 보냈는지 증명하기 위해서다. 나중에 "그 도면을 받은 적 없다"거나 "옛 Rev로 시공했다"는 다툼이 생기면 Transmittal 기록이 근거가 된다.
</details>
